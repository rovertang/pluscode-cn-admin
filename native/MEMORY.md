# 内存、按需查询与车辆移动

## 为什么任意位置查询也不需要全量加载

全国数据库是带主键索引的 SQLite 文件，不是必须整体反序列化的对象。一次查询先算出 Plus Code 前缀，再通过主键定位对应块。因此，从北京跳到广州只需要加载广州对应的一个混合块，不需要把两点之间的地图读进内存。

V2 的树已经适合这种方式：

| 层级 | 空间跨度 | 运行时处理 |
| --- | --- | --- |
| 4 位 | 1° × 1°，南北约 111 km | 小型顶层目录常驻；大面积单一归属直接返回 |
| 6 位 | 0.05° × 0.05°，南北约 5.56 km | 单一归属直接查目录，混合区域才从 SQLite 取块 |
| 8/10/11 位 | 逐级细化，最细米级 | 在命中的块内沿路径解析；粗码歧义时汇总相应子树 |

3,213 条 4 位目录本身远小于全国地图。运行时保留这些目录和行政区字典，比按位置反复换入顶层目录更简单，且可以立即回答大面积内部格。真正较大的内容是 92,174 个混合块，全部留在磁盘上按需读取。一个块的 XZ 流需要完整解压，块内不展开成全量 C++ 树对象；首次加载会扫描验证该块结构，后续热查询沿路径跳过无关子树。

## 默认策略

- 默认最多缓存 64 个混合块，解压缓冲区的容量合计最多 8 MiB；两个条件同时生效。
- 缓存采用 LRU。命中时更新最近使用顺序，加载新块时淘汰最久未使用的块。位置跳跃也直接加载目标块。
- 启动时混合块加载数为 0；缓存预算按实际增长，不预分配 8 MiB。
- SQLite 显式设置 `mmap_size=0`，避免映射整个数据库；页缓存目标设为 2 MiB。
- 单块大于缓存预算时仍可临时解压并完成查询，但不留入缓存。因此缓存预算为 0 也支持全国任意位置查询。
- 同一个实例串行保护 SQLite 和 LRU。多实例可并行，但每个实例有独立目录、字典和缓存，内存会叠加。

块缓存之外还有行政区 JSON 字典、目录、SQLite 页、解压器字典、当前块、查询结果和运行时分配开销。XZ 解码器允许的内存上限为 128 MiB，解压结果限制为每块 64 MiB，这是损坏/异常块防护上限，绝不代表常态占用，也不意味着总进程有这个硬上限。Java 堆和 JVM/ART 自身开销另外计算。

`cached_bytes` 按解压 `vector` 的实际 capacity 计费，包含该缓冲区的预留空间。它不包含容器节点和分配器元数据。`clear_cache()` 释放块、请求 SQLite 释放可回收页缓存；系统分配器和 OS 可能保留释放的内存，因此进程 RSS 不保证马上下降。

## 车辆定位建议

通常只创建一个长期存活的实例，在后台线程持续调用 `lookup_latlng` / `lookupLatLng` 就能自动完成随位置加载。不要每次 GPS 更新都打开和关闭全国数据库。

可选预热示例：

```cpp
pluscode_admin::Index index(database, {64, 8 * 1024 * 1024});
index.prefetch_nearby(latitude, longitude, 1, 9);
auto result = index.lookup_latlng(latitude, longitude);
```

```java
index.prefetchNearby(latitude, longitude, 1, 9);
PlusCodeIndex.Result result = index.lookupLatLng(latitude, longitude);
```

`radius_tiles=1` 表示以所在 6 位格为中心的 3×3 格邻域；只预热其中确实需要解压的混合块。单一归属块已在目录里，不需磁盘 I/O。预热最多访问 `max_tiles`、实例块数上限和候选数三者的最小值，近格优先选择，加载顺序让近格最后进入 LRU。缓存字节限额仍然生效，最终保留数可能少于访问数。返回报告包含 `candidate_tiles`、`visited_tiles`、`loaded_tiles`、`retained_tiles`。

这是同步、可失败的、尽力而为的缓存提示，不是独立后台线程，也不会固定锁住这些块。预热中出现坏块时抛错，此前已加载的块可保留。只对预期会经过的方向/邻域低频预热即可；连续定位已经能自然复用缓存。不要对每一个定位点都预热大范围，否则会造成额外解压和缓存淘汰。

## 约 110 km 的加载范围

4 位格正是用户提出的约 110 km 南北跨度层级，但它是目录，没必要把其下所有细节都载入。`radius_tiles=10` 会覆盖 21×21 个 6 位格，南北跨度约 117 km；`max_tiles` 可限制其中实际加载的混合块数。

这些格按角度定义，经度方向实际宽度随纬度乘以 cos(latitude)，因此并不是固定 110 km × 110 km 的米制方框。邻域以所在网格为中心，不是以原始坐标精确居中。日期变更线会环绕，极区越界行会跳过。API 支持 `radius_tiles=0..20`、`max_tiles=0..1024`。当前实现不做道路走廊预测和自动轨迹推断。

若车端内存更紧，可先使用 16 块/2 MiB，通过统计观察命中率和加载数后调整。若冷查询尾延迟比文件大小更重要，后续可以评估用更快的压缩算法重打包块；当前版本保持 V2 文件兼容，无需重新生成全国索引。

## 如何看统计

| 字段 | 含义 |
| --- | --- |
| `cached_tiles` / `cached_bytes` | 当前缓存块数 / 解压缓冲区容量字节数 |
| `capacity_limit` / `byte_limit` | 实例配置的两种缓存上限 |
| `hits` / `misses` | 混合块缓存访问命中 / 未命中次数；目录直接返回不计入 |
| `loads` | 已成功解压并通过验证的块加载次数 |
| `evictions` | 因 LRU 限额淘汰的块数；主动清空不计入 |
| `compressed_bytes_read` | 从 SQLite 获取的压缩 BLOB 累计字节数；不是物理磁盘读取量 |
| `sqlite_cache_bytes` | SQLite 报告的当前页缓存占用，含其相关开销 |
| `root_count` / `admin_count` | 常驻目录记录数 / 行政区记录数 |

计数器从打开实例起累积，清缓存不会归零。OS 文件缓存也可能命中，因此需要区分“块未命中”“读取 BLOB”“真正读磁盘”。实测报告见 [VALIDATION.md](VALIDATION.md) 和 `../validation/native/memory.jsonl`，以运行记录为准。

实现依据：[SQLite cache_size](https://www.sqlite.org/pragma.html#pragma_cache_size)、[SQLite mmap_size](https://www.sqlite.org/pragma.html#pragma_mmap_size)。SQLite 的页缓存设置是目标值，不是整个进程内存硬限额。
